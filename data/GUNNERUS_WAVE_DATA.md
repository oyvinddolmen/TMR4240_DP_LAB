# Gunnerus wave-load database (`gunnerus_vessel.json`)

`models/waves.py` computes the first-order (wave-frequency) and second-order
(slowly varying drift) wave loads from a hydrodynamic database of R/V
Gunnerus: force RAOs (amplitude and phase per DOF, 36 frequencies × 36
relative headings) and wave-drift coefficients, originally exported from a
ShipX (Veres) analysis. The file in this folder is a **corrected copy** of
the database shipped with `mcsimpy` (`vessel_data/gunnerus/vessel.json`),
generated by a course-maintained repair script. Do not edit it by hand.

## Why a corrected copy is needed

The `mcsimpy` file has two export defects (reported upstream), and the
wave-load code adds an interpolation hazard that the stored representation
must respect:

1. **Corrupt force-RAO phases for relative headings 0–180°.** In those
   columns the `phase` table is byte-for-byte equal to the `amp` table, i.e.
   the "phases" are force amplitudes in N, read as degrees (values up to
   ~1.2·10⁷ °). Because the wave-load code interpolates phases linearly
   between neighbouring 10° heading columns, a heading change of 0.1° then
   sweeps the phase of every wave component by many full cycles. A small
   wave-frequency yaw oscillation of the vessel is thereby rectified into a
   large, unphysical low-frequency wave force: in head seas the DP vessel
   drifted ±20–50 m at ~100 s period; environments from the port side or
   astern behaved completely differently from their starboard mirror images.
2. **Wave-drift yaw moment silently lost.** `mcsimpy.waves.wave_loads`
   expects the MSS drift-table layout (surge, sway, yaw stored in the first
   three cells, as written by MSS Hydro's `read_veres_WD.m`) and remaps
   cell 3 → yaw internally. `vessel.json` instead stores yaw drift in the
   standard sixth row, so the remap replaced the real yaw drift with zeros —
   the simulated vessel felt **no mean wave yaw moment at all** (no
   weathervaning tendency).
3. **Phase interpolation is branch-sensitive.** Phase is an angle, but the
   load code blends the stored numbers linearly across heading and frequency.
   Wherever two adjacent table entries lie on different 360° branches (for
   example −180° next to +180°, the same physical angle), the straight-line
   blend takes the long way around the circle and can invert the sign of the
   load between grid points. A vessel oscillating across such a seam
   rectifies wave-frequency load into a spurious slowly varying force or
   moment — visible as a port/starboard asymmetry of the slowly varying yaw
   moment, because only one half of the table carried such seams.

## What the corrected file changes

* The corrupt phase columns are reconstructed from the healthy 190–350°
  half using port/starboard symmetry of the complex response
  `H(ω, β) = amp·e^{iφ}`: surge/heave/pitch mirror as `H`, sway/roll/yaw as
  `−H` (the rule of the original MSS Hydro reader, `read_veres_TF.m`). The
  amplitude table — verified mirror-symmetric — is unchanged. The
  self-mirroring 0° and 180° columns copy their neighbouring column as an
  approximation (see Status).
* All phases are stored on a **branch-continuous surface**: adjacent entries
  along heading and frequency never differ by more than 180° where the
  amplitude is significant. Only multiples of 360° are added, so
  `e^{iφ}` — the physical content — is untouched; linear interpolation then
  always takes the shortest angular path. In addition, `models/waves.py`
  interpolates the RAO in complex form, which is branch-independent by
  construction.
* The drift yaw row is moved to the cell the load code reads, so the yaw
  drift is active again.

## Validation

Verified in `notebooks/part_2_waves_verification.ipynb`, section 7 (the same
tests are run whenever the database is generated):

* Amplitudes identical to the source; the healthy phase columns are
  physically identical (max |Δe^{iφ}| ≈ 10⁻¹⁵).
* No >180° phase step between adjacent table entries — along heading, along
  frequency, and across the 350°→0° seam — where the amplitude is
  significant.
* Drift table: surge symmetric, sway and yaw antisymmetric across
  port/starboard (to the source data's single precision), yaw drift nonzero.
* Mirrored seas: the same wave realisation from mirrored directions gives
  surge-force correlation +1 and sway/yaw correlation −1 for every tested
  heading pair.
* Boundary scan over all 36 heading grid boundaries: the first-order load is
  continuous across each boundary (worst normalized residual 0.120), and a
  ±2° wave-frequency heading oscillation across a boundary adds negligible
  low-frequency load (worst rectified mean 0.013 of the local WF load scale).
* Second-order (Newman) loads use the interpolated 360-entry QTF heading
  grid and a nonzero yaw drift.

## Status

The 0–180° phase half of this database is a symmetry-based reconstruction
from the healthy 190–350° half (exact for a symmetric hull up to the
approximated 0°/180° columns), not re-exported ShipX data; a regenerated
upstream dataset may replace it in a later course edition. The 0° and 180°
phase columns are copied from their 10° neighbours: head and following seas
at zero heading (Part 2, Simulation 5, directions 0° and 180°) use exactly
these two columns, with exact amplitudes and approximated phases. Use only this file
for the project simulations: results obtained with the uncorrected upstream
database are not comparable — waves from the port side/astern were wrong, and
no wave yaw moment acted on the vessel.
